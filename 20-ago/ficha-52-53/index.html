Actividad de aprendizaje · 8 horas
AA3

Elaborar el plan de instalación

Plataformas de desarrollo e implantación: LAMP, WAMP, XAMPP, WIMA. Primer contacto con máquinas virtuales y contenedores.

Concepto base

Un stack es una receta

Una página web no se abre sola en un servidor. Necesita cuatro ingredientes que trabajan en capas, y el stack es la combinación ya probada de esos cuatro.

Capa 1
Sistema operativo
Linux, Windows o macOS. Es la mesa donde se apoya todo lo demás.
Capa 2
Servidor web
Apache o Nginx. Recibe la petición del navegador y entrega la página.
Capa 3
Base de datos
MySQL o MariaDB. Guarda usuarios, productos, publicaciones.
Capa 4
Lenguaje
PHP, Python o Perl. Pone la lógica: calcula, consulta, decide.
Si cambia un ingrediente, cambia el nombre del stack. Eso es todo lo que significan las siglas.
Analogía: el stack es como un combo de restaurante. Los mismos ingredientes se pueden comprar por separado, pero el combo ya viene armado y probado.
Comparación

Las siglas, sin misterio

Plataforma Sistema operativo Servidor Base de datos Lenguaje
LAMP Linux Apache MySQL / MariaDB PHP · Python · Perl
WAMP Windows Apache MySQL PHP
MAMP macOS Apache MySQL PHP
XAMPP Multiplataforma (X) Apache MariaDB PHP · Perl
WIMA / WISA Windows IIS MySQL o SQL Server ASP.NET
MEAN / MERN Node.js Express MongoDB JavaScript
Para la evidencia: XAMPP es la opción más cómoda si trabajan en Windows, porque instala Apache, MariaDB y PHP en un solo paso.
Pedir que identifiquen la letra que cambia en cada fila: casi siempre es el sistema operativo o el servidor web.
Antes de instalar

La plataforma se elige por requisitos

Los requisitos funcionales dicen qué hace el sistema. Los no funcionales dicen cómo debe comportarse, y son los que deciden la arquitectura.

Rendimiento
Cuántos usuarios simultáneos y con qué tiempo de respuesta.
Disponibilidad
Cuántas horas al año puede estar fuera de servicio.
Escalabilidad
Si debe crecer y cómo: más máquinas o máquinas más grandes.
Seguridad
Cifrado, control de acceso, protección de datos personales.
Compatibilidad
Sistemas operativos, navegadores y versiones que debe soportar.
Mantenibilidad
Qué tan fácil es actualizar, respaldar y monitorear.
Ejemplo concreto: si el cliente exige 99,9% de disponibilidad, un solo servidor local no alcanza. Ese requisito no funcional obliga a pensar en clúster, que es justamente AA4.
Práctica

Desplegar la plantilla en local

  1. Descargar una plantilla HTML gratuita y descomprimirla.
  2. Instalar la plataforma elegida (por ejemplo XAMPP) con las opciones por defecto.
  3. Abrir el panel de control e iniciar los servicios Apache y MySQL.
  4. Copiar la carpeta de la plantilla dentro de C:\xampp\htdocs\.
  5. Verificar en el navegador: http://localhost/mi-plantilla/
  6. Capturar pantalla de cada paso mientras lo hacen, no después.
Si el puerto 80 está ocupado (Skype, IIS u otro programa), cambien Apache al puerto 8080 y prueben con http://localhost:8080/.
Error clásico: dejar la plantilla en Descargas y abrirla con doble clic. Eso abre el archivo, no lo sirve. Debe verse localhost en la barra de direcciones.

AA4

Configurar los servicios requeridos

Clústeres, análisis de riesgo e impacto, RPO y RTO, recuperación de desastres y continuidad del negocio.

Concepto base

Disponibilidad se mide en nueves

Disponibilidad es el porcentaje de tiempo que el servicio responde. Se ve pequeño en la tabla, pero la diferencia entre un nueve y otro es enorme.

Nivel Disponibilidad Fuera de servicio al año Ejemplo típico
Dos nueves 99 % 3 días y medio Sitio informativo pequeño
Tres nueves 99,9 % 8 horas y media Comercio electrónico
Cuatro nueves 99,99 % 52 minutos Banca en línea
Cinco nueves 99,999 % 5 minutos Telefonía, salud, pagos
Cada nueve adicional multiplica el costo. Por eso la disponibilidad se negocia con el cliente en un acuerdo de nivel de servicio (SLA), no se promete de más.
Preguntar al grupo: ¿cuántos nueves necesita la plataforma de matrículas del SENA? Es un buen debate porque la respuesta depende del momento del año.
Principio de diseño

Redundancia: nunca una sola pieza crítica

Un punto único de falla (SPOF) es cualquier componente que, si se daña, tumba todo el servicio. Redundancia es tener repuesto listo para cada uno.

Energía
UPS y planta eléctrica. Dos acometidas independientes.
Red
Dos proveedores de Internet y switches duplicados.
Servidores
Varios nodos atendiendo detrás de un balanceador.
Almacenamiento
RAID y réplicas de la base de datos en otra máquina.
Datos
Copias de seguridad probadas y guardadas en otro sitio.
Personas
Más de una persona sabe operar el sistema y hay documentación.
La llanta de repuesto no sirve si nunca se revisó. Un respaldo que nunca se ha restaurado no es un respaldo, es una esperanza.
Buen momento para preguntar cuál es el SPOF más común en los proyectos de los aprendices: casi siempre es que el proyecto vive solo en el portátil de una persona.
Arquitectura

Un clúster es un equipo de máquinas

Varios computadores (nodos) conectados que se comportan hacia afuera como uno solo. Si un nodo cae, los demás siguen atendiendo.

01
Nodos
Los servidores que hacen el trabajo real. Pueden ser físicos o virtuales.
02
Balanceador de carga
Reparte las peticiones entre los nodos disponibles. HAProxy, Nginx, ELB.
03
Heartbeat
Señal periódica que confirma que cada nodo sigue vivo.
04
IP virtual
Una sola dirección de entrada que se mueve al nodo que esté activo.
05
Almacenamiento compartido
SAN, NAS o replicación para que todos vean los mismos datos.
06
Failover
El traspaso automático de la carga cuando un nodo falla.
Herramientas para nombrar en el informe: Pacemaker y Corosync, Keepalived, HAProxy, Kubernetes, MySQL Group Replication, Proxmox VE, VMware vSphere HA.
Clasificación

Tres tipos, tres propósitos

Alta disponibilidad
Objetivo: que el servicio no se caiga. Nodos en activo-pasivo o activo-activo con failover automático. Ejemplo: base de datos de un hospital.
Balanceo de carga
Objetivo: atender mucho tráfico. Las peticiones se reparten entre nodos iguales. Ejemplo: tienda en línea en temporada alta.
Alto rendimiento (HPC)
Objetivo: resolver un cálculo enorme. Los nodos se reparten partes del mismo problema. Ejemplo: modelos del clima.

Tipos de procesamiento

Paralelo
El trabajo se divide y se ejecuta al tiempo en varios nodos.
Distribuido
Tareas independientes repartidas entre nodos que se coordinan por red.
Por lotes o transaccional
Colas de trabajos programados, u operaciones cortas y constantes.
Activo-activo: todos los nodos trabajan. Activo-pasivo: uno trabaja y el otro espera. El primero aprovecha más recursos, el segundo es más simple de configurar.
Métricas de recuperación

RPO y RTO en una línea de tiempo

Son las dos preguntas que todo cliente debe responder antes de un desastre: cuántos datos puedo perder y cuánto tiempo puedo estar caído.

Último respaldo
Falla
Servicio restablecido
RPO · datos que se pierden
RTO · tiempo sin servicio
RPO se reduce respaldando más seguido o replicando en tiempo real. RTO se reduce con failover automático y procedimientos ensayados.
Ejemplo para fijar la idea: si respaldo cada 24 horas, mi RPO es de 24 horas; si la falla ocurre a las 11 p.m. perdí casi un día completo de registros. Preguntar cuánto valdría ese día en una tienda.
Gestión

Del riesgo al plan de continuidad

  1. Análisis de riesgo. Qué puede fallar, con qué probabilidad y con qué impacto.
  2. Análisis de impacto (BIA). Cuánto cuesta cada hora caído en dinero, reputación y aspectos legales.
  3. Gestión de prioridad. Qué servicios se levantan primero: los críticos antes que los accesorios.
  4. Plan de recuperación de desastres (DRP). Procedimiento técnico para volver a operar.
  5. Plan de continuidad del negocio (BCP). Cómo sigue funcionando la organización mientras se recupera.
  6. Gestión de crisis y pruebas. Quién decide, quién comunica, y simulacros periódicos.
Un plan que nunca se ha probado es un documento, no un plan. Las pruebas de operación son las que lo vuelven real.
Aclarar la diferencia DRP vs BCP: el DRP es técnico, el BCP es organizacional e incluye personas, sedes alternas y comunicación con clientes.
Balance honesto

Los clústeres también cuestan

Ventajas
Alta disponibilidad y tolerancia a fallos.
Escalabilidad horizontal: se agregan nodos.
Mejor rendimiento bajo mucha carga.
Mantenimiento sin apagar el servicio.
Recuperación más rápida ante desastres.
Desventajas
Mayor costo en equipos, licencias y red.
Configuración y operación complejas.
Requiere personal con más especialización.
Sincronizar datos entre nodos es difícil.
Riesgo de split-brain si se pierde el heartbeat.
Regla práctica: la arquitectura debe costar menos que la caída que evita.
Split-brain: dos nodos creen que son el activo y escriben al tiempo, corrompiendo los datos. Se evita con quórum y con dispositivos de aislamiento (fencing).

AA5

Configurar el software en el servidor y la base de datos

La actividad más extensa: montar Ubuntu con Apache y MySQL, primero virtualizado y después en contenedores.

Concepto base

Virtualizar es partir una máquina en varias

Un programa llamado hipervisor toma el hardware real y lo reparte entre varias máquinas virtuales, cada una con su propio sistema operativo completo.

Hipervisor tipo 1 · bare metal
Se instala directamente sobre el hardware, sin sistema operativo debajo. Más rápido y seguro. Se usa en centros de datos.

VMware ESXi · Proxmox VE · Hyper-V · KVM
Hipervisor tipo 2 · hospedado
Se instala como un programa más dentro de Windows o macOS. Más fácil de usar, algo más lento. Ideal para aprender y probar.

VirtualBox · VMware Workstation · UTM
Para la evidencia usen tipo 2: VirtualBox es gratuito y corre en cualquier portátil con 8 GB de RAM.
Si el aprendiz ve el error VT-x deshabilitado, debe activar la virtualización en la BIOS. Es la falla más frecuente de esta actividad.

La diferencia está en una sola capa: el contenedor no lleva su propio sistema operativo, comparte el núcleo del anfitrión. Por eso pesa megabytes y arranca en segundos, mientras la máquina virtual pesa gigabytes y arranca en minutos.
Analogía: la máquina virtual es una casa completa con cimientos propios; el contenedor es un apartamento en un edificio, con paredes propias pero estructura compartida.

En la nube casi siempre se usan los dos: contenedores que corren dentro de máquinas virtuales.
Mencionar que Kubernetes orquesta contenedores sobre nodos que suelen ser máquinas virtuales. Así queda claro que no es o lo uno o lo otro.
Ruta A · primera parte del informe

Ubuntu con Apache y MySQL en VirtualBox

  1. Instalar VirtualBox y descargar la ISO de Ubuntu Server.
  2. Crear la máquina: 2 CPU, 2 GB de RAM, 20 GB de disco, red en modo puente.
  3. Instalar Ubuntu y actualizar el sistema.
  4. Instalar y verificar los servicios.
# actualizar el sistema
sudo apt update && sudo apt upgrade -y

# servidor web
sudo apt install apache2 -y
sudo systemctl enable --now apache2

# base de datos
sudo apt install mysql-server -y
sudo mysql_secure_installation
Red en modo puente para poder entrar desde el navegador del anfitrión con la IP de la VM. Con NAT tocaría redireccionar puertos.
Ruta B · segunda parte del informe

Lo mismo, en contenedores

Un archivo docker-compose.yml describe la misma máquina: servidor web, base de datos y la plantilla publicada. 

services:
  web:
    image: httpd:2.4
    ports: ["8080:80"]
    volumes: ["./sitio:/usr/local/apache2/htdocs"]

  db:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: claveSegura
      MYSQL_DATABASE: pruebas
    ports: ["3306:3306"]
    volumes: ["datos:/var/lib/mysql"]

volumes:
  datos:
docker compose up -d
docker ps
Compare los tiempos: instalar la VM toma cerca de media hora; levantar estos contenedores toma menos de un minuto. Esa comparación es material excelente para las conclusiones.
El volumen datos hace que la base de datos sobreviva si se borra el contenedor. Buen momento para explicar persistencia.

AA6

Cargar archivos en el sitio de publicación

Publicación tradicional: hosting, dominio, DNS y carga de archivos por FTP.

Concepto base

Tres cosas distintas que se confunden

Hosting
La casa. El espacio en un servidor encendido las 24 horas donde viven sus archivos.
Dominio
La dirección. El nombre fácil de recordar que la gente escribe en el navegador.
DNS
El directorio. Traduce el nombre a la dirección IP donde está la casa.
Se contratan por separado y luego se conectan: en el panel del dominio se apuntan los registros DNS (A o NS) hacia el servidor del hosting. Ese apunte puede tardar unas horas en propagarse.
Si el sitio no carga después de configurar el dominio, casi siempre es propagación DNS. Se verifica con nslookup o dnschecker.org antes de tocar nada más.
Panorama

Del más compartido al más propio

Tipo Cómo funciona Cuándo conviene
Compartido Muchos sitios en un mismo servidor, con panel tipo cPanel Sitios pequeños y prácticas académicas
VPS Una máquina virtual con recursos reservados y acceso root Proyectos que necesitan configuración propia
Dedicado Un servidor físico completo para un solo cliente Alto tráfico o exigencias de cumplimiento
Nube Recursos elásticos que crecen y decrecen bajo demanda Cargas variables, se paga por consumo
Estático / Pages Solo HTML, CSS y JS servidos desde una CDN Plantillas, portafolios, documentación
Conectar con AA4: la redundancia y el clúster que estudiamos son justamente lo que el proveedor de hosting ya montó por dentro.
Para la práctica

Alternativas sin costo

Hosting con panel y FTP
InfinityFree, GoogieHost, AwardSpace. Ofrecen panel de control, FTP y base de datos MySQL. Son los que mejor se parecen a un hosting real y por eso sirven para mostrar el proceso tradicional completo.
Hosting estático desde repositorio
GitHub Pages, Netlify, Vercel, Firebase Hosting. Publican en minutos y con HTTPS, pero solo sitios estáticos y sin FTP: se sube por Git o arrastrando la carpeta.
Sobre el dominio gratuito: lo que casi siempre se obtiene sin costo es un subdominio del proveedor, del estilo miproyecto.host.com. Un dominio propio, con extensión como .com, normalmente se paga. Verifiquen condiciones antes de elegir, porque estos servicios cambian con frecuencia.
Aclarar que si eligen GitHub Pages no habrá capturas de FTP; en ese caso deben documentar el flujo con Git. Ambas rutas son válidas mientras el sitio quede accesible por Internet.
Práctica

De la carpeta local a Internet

  1. Crear la cuenta en el proveedor de hosting y confirmar el correo.
  2. Registrar el dominio o subdominio y anotar los datos entregados.
  3. Apuntar los registros DNS del dominio hacia el hosting.
  4. Obtener las credenciales de FTP: servidor, usuario y contraseña.
  5. Conectarse con FileZilla y subir la plantilla a la carpeta htdocs o public_html.
  6. Verificar que el archivo principal se llame index.html.
  7. Activar el certificado SSL y abrir el sitio con https://.
Error frecuente: subir la carpeta comprimida o dejar el sitio dentro de una subcarpeta. Los archivos van sueltos en la raíz pública.
Pedir que la captura final muestre la URL pública completa en la barra de direcciones y el candado del certificado.
